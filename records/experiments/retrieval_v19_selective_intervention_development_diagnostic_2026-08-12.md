# V19 选择性干预 development 诊断

日期：2026-08-12
结论：**当前候选不发布、不冻结、不运行holdout。**

## 范围与数据治理

- 50个来源家族、每家族4条查询，共200条；development/holdout各100条。
- 可回答与无答案各100条；四个查询角色各50条。
- 200个query ID和200条自然语言查询均唯一。
- 本轮模型、检索、阈值扫描和错误分析只执行development的100条。
- holdout未运行检索、未计算指标、未用于选择参数。
- 私有查询、图像绑定和逐条结果位于Git忽略目录；本文只发布聚合统计。

## 路由层诊断

| 指标 | 结果 |
|---|---:|
| development查询数 | 100 |
| 本地LLM调用数 | 59 |
| 原始路线变化建议 | 29 |
| guarded实际放行 | 13 |
| 安全门控拦截 | 16 |
| 模型/解析回退 | 0 |
| 路由P50 | 约1.14秒 |

16次拦截中，14次属于“事实查询→发现模式”，另外2次会移除冻结V18
所需证据分支。这验证了报告中的核心判断：语义路由不能直接控制执行策略，
必须保留冻结V18回退和危险迁移门控。

候选没有达到预注册的Top-1至少+5pp、Recall@3至少+5pp和P95不超过
1.10倍三个门槛。尤其是Top-1下降且P95约为基线的3.75倍，因此不应以
“拒答略有改善”为由进入最终留出评测。

## 属性证据与晚交互诊断

development中50个可回答查询有25个已将目标页排到Top-1，但其中10个被
拒答器误拒。58条自然查询触发旧属性门控，58条均被“全部必要属性必须
逐项通过”的未校准规则拒绝。

只放宽覆盖率也不能解决问题：在约2/3覆盖率且FAR不增加时，Top-1仅从
30%恢复到32%；继续放宽会显著增加错误接受。因此本轮没有采用阈值刷分。

对13条实际干预样本运行Qwen3-VL-Reranker-2B晚交互：

- 单一完整查询分数在7个可回答样本中将6个目标页排到首位；
- 但它也对只改变数量或方向的强负例给出相近高分；
- 属性级验证耗时42.347秒（含5.746秒加载），峰值显存4.512 GiB；
- 现有分解器与验证器仍不能可靠区分“三块/四块”“上方/下方”等反事实。

所以“全局Reranker高分即接受”不成立。后续方法必须同时具备最弱必要条件
证据、正反关系差值和低成本执行，不能再让单一高相似属性主导结果。

## 后续允许的研究方向

1. 为数量、方向和绑定关系生成显式正反条件，并要求正向证据高于反事实。
2. 修复自然查询分解，避免把页面/图片等容器词误当作必要对象。
3. 将昂贵晚交互限制到极小争议池，或蒸馏为低成本属性判别器。
4. 先在development达到全部发布门槛，再冻结方法并申请一次holdout运行。

在这些条件满足前，V18.1继续作为公开稳定版本，V19保持研究分支状态。
